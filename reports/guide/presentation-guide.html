Two things that will bite you on stage

Timing needs 32 transactions before it can score anything. Its window is empty at startup. The detector pages fill it automatically now, but if you demo the live monitor with a short file, Timing will abstain.

The Query Runner writes to Neon Postgres, and the monitor reads from the same place. If the monitor shows nothing after an upload, that connection is the first thing to check.

Handing GraphSAGE to someone else

The detector on its own — code, trained weights, and the prebuilt graph that git excludes — is packaged at ~/Downloads/DeepSentinel-GraphSAGE-Setup.zip (71 MB, unpacks to 393 MB). It runs anywhere it is unzipped, with no database and no network access after install.

unzip DeepSentinel-GraphSAGE-Setup.zip
cd DeepSentinel-GraphSAGE-Setup
python3 -m venv .venv && source .venv/bin/activate
pip install -e .        # the -e matters
./run.sh                # serves on :8002

It contains the 162 MB serving bundle, the node-name index, the v2 node features, all five ablation checkpoints, the per-stage reports, the EDA figures, and a labelled demo CSV. START-HERE.md inside covers running it, retraining it, and what each artefact is for.

The -e is not cosmetic: the service finds data/ by walking up from its own source file, so a non-editable install sends it looking inside site-packages.

Sixty-second sanity check before you leave the house

  1. Open the console. The sidebar footer should say All models ready.
  2. Go to Fusion. The five pipeline stages should all be green.
  3. Go to Network. Open the explorer, search C1988852187, see the graph.

01 What the system is

Three independent fraud detectors look at the same transaction from three different angles. A fourth component weighs their opinions into one verdict, looks the pattern up against known money-laundering typologies, writes the case up, and delivers it.

DETECTOR
Network
Who pays whom, two steps out. Yours.
DETECTOR
Behaviour
Does this fit its own transaction type?
DETECTOR
Timing
The 32 transactions it arrived among.
FUSION
One verdict
Weighs the three. Member 4's.
EVIDENCE
Report
Typology, narrative, PDF, email.
Say this A single model sees one kind of evidence. Fraud leaves three kinds. The contribution is not a better detector — it is combining three so that the one which happens to see the fraud carries the verdict.

Where the data lives — this matters

There are two separate stores and they never touch.

The bundleThe database
holdsa frozen PaySim graph: 3,277,509 accounts, 2,770,409 transfers, plus every account's precomputed score the live queue, analyses, cases, audit log
used bythe Network detector only the monitor and the console
changesnever — it is historyconstantly

So clearing the database does not empty the graph explorer. The graph service contains no database code at all. If asked, that is correct behaviour: the bundle is the history the model reasons about, not a view of today's traffic.

Where the models sit

The Query Runner writes arriving transactions into transactions_live. The monitor polls that table, claims a batch with FOR UPDATE SKIP LOCKED, and calls all three detectors in parallel. The Query Runner never talks to a model — the database is the queue between them. Nothing is lost if a detector is down: the row is already committed before any model sees it.

03 GraphSAGE, A–Z

The gap

Fraud detection normally judges one payment on its own: amount, balance, time. Judged that way, moving stolen money is nearly invisible — it is done in small ordinary steps. The shape only appears when you look at how accounts are joined to each other.

And the accounts that matter are always new. A model that can only recognise accounts it has seen before is blind to exactly the ones used to receive stolen money.

The three novelties, and what each turned out to be worth

NoveltyWhat it doesMeasured
1 · Edge-MLP attention
models/layers.py		 Weighs each transfer by how unusual it is, instead of treating every edge as equal. No measurable effect (n=12, p=0.73). Section 03's ablation explains why, and why finding that is a result.
2 · Sampler + focal loss
sampling/, training/losses.py		 Fraud is 1 in 773. Training is arranged so the model is not simply rewarded for saying no. Works. The sampler alone is worth +0.16 test F1 — the largest single contribution.
3 · Subgraph extractor
extraction/subgraph.py		 Returns the cluster of accounts behind the score, with per-edge attention — evidence, not just a number. Explainability, not accuracy. Unaffected by the above.
Say this about focal alpha We use α = 0.95, not the 0.25 from the original focal-loss paper. That value is for object detection. On a 773:1 imbalance it puts most of the weight on the majority class and the model converges to predicting no-fraud for everything. Choosing it deliberately is the point.

Data preparation

  1. Download PaySim — scripts/download_paysim.py.
  2. Six edge features — scripts/prepare_features.py: amount_log, drain_ratio, src_drained, dst_was_empty, time_gap, type_is_transfer.
  3. Twelve node features — degrees, mean and max amounts, amount uniformity (smurfing), fan-in/out distinctness, outgoing drain, fresh-receiver ratio, velocity, first appearance. Count-like columns are log1p-scaled so degrees do not drown out ratios.
  4. Build the graph — scripts/build_temporal_graph.py.

The finding to lead with

Stage 2 scoring below the baseline it extends was not a result about attention — it was a bug in our own layer. SAGEConv aggregates with mean; our edge layer used an unnormalised add, so stage 2 vs 1 changed two things and never isolated attention. In-degree reaches 75, so hub activations scaled with degree.

Correcting it to an attention-weighted mean took stage 2 from 0.0585 to 0.2777 val F1 — PR-AUC up ten-fold. Gradient clipping and a changed initialisation did nothing, which rules out the two obvious alternatives.

Does edge attention help? No — and that is measured, not assumed

With the aggregation fixed, twelve seeds per arm:

ConfigurationnVal F1
3b* with attention120.3645 ± 0.0035
3c without it120.3650 ± 0.0036

Difference −0.0005, Cohen’s d = −0.14, p = 0.729. At three seeds attention appeared 0.0045 ahead; under power that reversed sign.

Say this, precisely Attention does not hurt — that was the aggregation bug. And this is not “inconclusive”: twelve seeds per arm around d = −0.14 is a positive finding of no effect. In hindsight the six edge features are largely redundant with the twelve node features, which already encode the same drain-to-empty event.
Why the leave-one-out arm mattered

The additive chain 1 → 2 → 3a → 3b would have shown stage 2 failing and invited the conclusion that attention does not work on sparse graphs. It was stage 3c — the arm that removes the component from the finished system — that exposed the contradiction: a component cannot be both useless in isolation and load-bearing in situ. Designing that arm is what caught a bug in our own code.

Why recall is only 0.27 — have this ready

PaySim’s graph is 507,100 disconnected components and the largest has 90 accounts. Every one of the four biggest is a tree — exactly n−1 edges, no cycles. Almost every sender makes one transfer and vanishes. For most accounts there is barely any neighbourhood to read. That is a property of the data, and it is why fusing three detectors matters.

How the meta-classifier works

Three detectors vote; the votes are weighted; the total is squashed to a probability. A StandardScaler followed by a logistic regression, so it decomposes exactly:

z = intercept + Σ coefficient · (score − mean) / scale

              mean     scale    coefficient
network      0.2891   0.2139       1.6549
behaviour    0.3162   0.2458       2.9429
timing       0.3635   0.2898       4.5059     intercept −2.4081

Worked through on a real case — row 84 of the showcase file:

DetectorScoreCentred× coefContribution

1 / (1 + e^−5.7418) = 0.9968 — exactly what the console reported. Behaviour voted innocent and was outvoted. One detector seeing the fraud is enough, which is the whole argument for fusing three.

This is not SHAP and not an approximation — for a linear model the attribution is the model, read back out.

When a detector does not answer

Its score is imputed at its own training mean — an absent opinion is neutral, not an argument for innocence — and the whole log-odds is shrunk by 0.18 per missing detector, so the number itself says less evidence went into it.

How a typology is matched — be precise about this

  1. Each score becomes a word: ≥0.75 high, ≥0.40 medium, else low.
  2. The words become a sentence — "Financial fraud with low graph network signal… Dominant detection modality is temporal analysis."
  3. That sentence is embedded and compared by cosine similarity against the ten typologies. Nearest wins.

The signal columns in the typology table are not what does the matching. They are metadata describing what each pattern expects — a check you can eyeball, not the mechanism.

05 Thresholds — the honest answer

There are two different thresholds in the system and they are justified differently. Do not conflate them.

1 — The Network detector's threshold: 0.1830

Principled. Tuned on the validation window for best F1, then frozen. Never touched test. The model publishes it on its own /health, and the console reads it from there rather than storing a copy. Its bands follow from it: high is exactly that threshold, medium is half of it, critical is the 99.5th percentile of scored accounts.

2 — The fused operating point: 0.80 / 0.65 / 0.50

Chosen, not derived — and say so. The fused score has no calibration of its own, so there is no principled value to compute. What justifies it is the Thresholds page, which replays stored decisions at a different line and shows what would have been caught and missed.

If a panel member pushes on the fused line

"It is an operating point, not a derived constant — the fused score is not calibrated, so there is nothing to derive. What we can defend is the trade-off: at 0.80 we get precision 1.000 and recall 0.559 on the held-out window. The page lets an operator move it and see that trade-off before committing."

Both come from one definition now, backend/thresholds.py. There were once four disagreeing copies — the page displayed one, the monitor fired on another, and every stored verdict was labelled by a third.

06 Validation — how to prove it live

Do not describe accuracy. Demonstrate it. Four things you can run in front of them.

1 · Upload a labelled file

Network → Demo mode → Upload a CSV, or Fusion → Score a file. Files live in ~/Downloads/deepsentinel demo/. Both panels read the label column, mark every row right or wrong, and report precision, recall and F1.

The pair to run back to back: graphsage_best_1000_fresh_receiver.csv (recall 0.389) and graphsage_hard_1000_established_receiver.csv (recall 0.014). Same size, same 72 frauds — recall differs 28× while accuracy moves 0.013. That contrast is the strongest argument you have for not quoting accuracy.

2 · Score an account that does not exist

Network → Demo mode. Invent an account, attach it to a real one, score it. Change only the amount: 500 → 0.2855, 5,000 → 0.7866, 200,000 → 0.9911. The account had no stored score; the model built one from the transaction you typed.

Do not demo this by changing the sender

Measured: ten different senders at the same amount all score between 0.8630 and 0.8751. On a one-transaction account there is no topology yet, so magnitude is the only feature that varies. The structural features earn their keep on accounts with a real neighbourhood — which is what the two 1,000-row files measure.

3 · Show it refusing bad input

Hand it an unrelated CSV: "missing required column(s): nameOrig, nameDest, amount, type, step." Type an amount of 0, or make an account pay itself — each is refused by name, next to the button. The API refuses more than the panel can produce by hand: a payment larger than the sender's balance, balances that do not match the amount, a step outside 1–743.

4 · Turn a detector off

Fusion → Live. On fraud case LK-2026-0041: network −1.77 (innocent), behaviour −1.30 (innocent), timing +7.62 (fraud). Fused = 0.8954, CRITICAL. With timing absent the same transaction scores 0.0111 — LOW. Two of three detectors are wrong and the system is still right.

07 Questions they will ask

Did all three of your novelties work?
No, and we measured it. The sampler is worth +0.16 test F1. The subgraph extractor is explainability, not accuracy. Edge attention showed no measurable effect — 12 seeds per arm, d = −0.14, p = 0.73. Getting to that answer meant finding and fixing a bug in our own layer first. Section 03 has the full account.
How do you know it is not overfitting?
Train, validation and test are separate time windows — steps 1–600, 601–700, 701–743. Features are recomputed per snapshot, so no training feature contains future information. The threshold was tuned on validation and test was used once.
Your accuracy is 0.919 — isn't that suspicious?
Yes, and it is on screen with the caveat. Flagging nothing at all scores 0.906. Precision 0.668 and recall 0.271 are the figures that mean something.
Why is recall so low?
The graph is extremely sparse — 507,100 disconnected components, the largest 90 accounts, and every large one is a tree. We can also show it precisely: recall falls from 0.364 when the receiver is a first-time receiver to 0.000 once it has six or more incoming transfers. It is a property of the data, and the reason we fuse three detectors.
Is this real data?
No — PaySim, simulated. Say it plainly. It is the standard public benchmark because real transaction data cannot be released. Production deployment would require validation on institutional data.
Show me the RAG.
Fusion → Typologies. Ten FATF typologies in ChromaDB, embedded with all-MiniLM-L6-v2, retrieved by similarity. The matched one is highlighted with its score.
Does the LLM make things up?
It can only cite the detector outputs and the retrieved typology — nothing else is passed to it. The pipeline diagram draws that constraint, and there is a grounded-vs-ungrounded comparison view.
What happens if a model goes down?
It abstains. Its score is imputed at its training mean and the verdict shrunk toward neutral by 0.18, so the number says less evidence went into it. Nothing crashes and no fake score is invented.
Why GraphSAGE and not a GCN?
GraphSAGE learns an aggregator — a function from neighbourhood to embedding — rather than one fixed embedding per node. That is what lets it score an account created after training. Mule accounts are always new, so a transductive model is blind to exactly the accounts that matter.

08 Limitations — state these first

A team that names its own limits is trusted on everything else it says.

  • Simulated data. PaySim, not real transactions.
  • Edge attention contributes nothing measurable on this graph. We report it as a null result with n = 12 per arm rather than quietly keeping the claim.
  • A very sparse graph. Most accounts transact once, so the network detector's recall is low by construction.
  • A flattering dataset. A single PaySim column (newbalanceDest == 0) reaches precision 1.000 and recall 0.502 with no model at all.
  • The fused operating point is chosen, not derived.
  • Demo-mode scores are uncalibrated. The isotonic calibrator was never saved as a reusable artefact, so the inductive path reports raw model output and the page says so.
  • Not certified for production financial decisioning.
Every number here was measured, not remembered — the ablation from three to twelve seeds per arm under temporal_snapshots_leakage_free, the rest read from the running system. Where a figure appears here it also appears on a page in the console, computed from the model rather than typed in.
